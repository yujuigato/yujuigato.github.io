Background

這個系統在解決什麼問題？

業務活動的報名、實際出席、問卷作答、聯絡人資訊，散落在不同系統裡，彼此用不同的鍵值互相對應；業務想知道「這個人上次活動聊了什麼、卡在什麼痛點、現在到什麼購買階段」，得手動跨系統拼湊，數萬筆規模下完全不可行。而如果要讓 AI agent 在通話前自動生成有根據的個人化話術，它也需要一份能被即時檢索、內容可信、結構統一的知識庫可用——這正是 RAG（Retrieval-Augmented Generation）架構裡最容易被低估、卻最花工夫的 Retrieval 層。

😣 過去的痛點

  • 報名、實到、問卷作答、聯絡資訊四套系統各自獨立，沒有統一的比對鍵
  • 問卷是開放式文字作答，沒有角色／痛點／購買階段等結構化標籤
  • 同一家公司多位員工出席同場活動，人工彙整容易漏算或算重
  • 下游若要做 AI 話術生成，沒有一份可信、即時、結構統一的知識庫可以檢索

✅ 系統如何解決

  • 以「公司 × 活動場次 × 年月」為 session 單位，串接四大來源
  • LLM 批次萃取角色、痛點摘要、需求、購買階段，統一輸出結構化欄位
  • 產出公司彙整／公司活動整合／人員明細三層知識庫，供下游即時查詢
  • 每日自動增量更新，確保下游 agent 檢索到的永遠是近兩年的最新脈絡
How It Works

系統如何運作？

為什麼說這是 RAG 架構的 Retrieval 層？

RAG 不是只有「向量資料庫 + embedding」一種形式——它的本質是「先檢索出可信的結構化上下文，再交給 LLM 生成」。這個 pipeline 做的正是前半段：把四散的原始資料，整理成三層結構化知識庫（公司彙整 / 公司活動整合 / 人員明細，各自帶近兩年脈絡與近期歷史紀錄），讓下游的話術推薦 agent 在通話前可以直接依「潛客代號」查到這個人／這家公司完整、可信的背景，再送進 LLM 生成個人化的開場白、提問與推進動作。沒有這一層，LLM 只能瞎猜；有了這一層，生成內容才有憑有據。

1

四大來源資料整合與清洗

撈取聯絡人基本資料、活動實際出席紀錄（非僅報名）、完整問卷 Q&A、身分對照表，過濾格式不合法的測試帳號與髒資料。

個人帳號缺公司名稱時，走第二來源補正；補不到者標記為「個人」，排除在公司層級彙整之外，避免污染知識庫
2

Session 組裝：公司 × 活動 × 年月

只有「確實出席」的紀錄才會組成 session，並從出席名單展開同公司當場的每一位實到者，共用公司層級的問卷內容。

問卷若被重複提交，只取最新一次作答，避免同一人歷史答案互相污染
3

LLM 批次結構化萃取

把每個 session 的問卷 Q&A 交給 Gemini Flash Lite，判斷聯絡人角色（決策者/評估者/使用者/影響者）、萃取核心痛點摘要、主要需求、購買階段標籤。

LLM 回傳「無」「不明」「暫無具體痛點」等雜訊語句，統一清洗為空字串，避免污染下游檢索結果
4

產出三層 RAG 知識庫

公司彙整（含近兩年活動數、最新購買階段、各角色痛點/需求分欄）、公司活動整合（單場次角色分布與整體痛點）、人員明細（個人層級痛點摘要＋近期歷史脈絡），供下游 agent 以「潛客代號」即時查詢。

Downstream Impact

這份知識庫的下游應用

🎯 成為業務話術推薦 Agent 的檢索層

這個 pipeline 輸出的三層知識庫，後續被另一個團隊用於建構「問卷舉手推薦」agent：業務要聯繫在活動問卷中表達意願的客戶前，agent 會以潛客代號從這份知識庫檢索出對方的角色、本次痛點摘要、近期歷史脈絡與公司整體購買階段，組成 RAG 的檢索上下文，再交給 LLM 生成通話前重點提醒與個人化的電話／Email 開場話術。這裡展示的是知識庫本身的設計與產出；下游話術生成 agent 的 prompt 設計與應用邏輯不屬於本專案範圍。

Engineering Challenges

解決了哪些技術難題？

Challenge 1

近 7 萬筆規模下的 LLM 成本控制

每個 session 都要跑一次 LLM 結構化萃取，若每次執行都重新分析全部歷史資料，成本與時間都無法接受。

↓ 解決方案

三層快取設計：已判斷信號永久快取、DB 問卷查詢快取 23 小時、已萃取 session 永久快取，中斷重跑不重複計費

Challenge 2

同公司多人共用問卷內容的正確展開

同一場活動同公司可能有多位員工出席，若用帳號層級去重會誤把多人算成一人，人數統計失真。

↓ 解決方案

以 Email 而非公司帳號代號計算參與人數，並在 session 組裝時展開每位實到者，各自保留獨立的問卷回應紀錄

Challenge 3

公司名稱髒資料污染知識庫

來源系統中夾雜含電話號碼、暫代字樣、純數字等異常公司名稱，直接寫入知識庫會讓下游檢索抓到錯誤實體。

↓ 解決方案

以規則偵測異常字串樣式，優先透過身分對照表回填正確公司名稱，找不到再用次要來源欄位 fallback

Challenge 4

知識庫必須即時反映最新脈絡

下游 agent 通話前檢索到的若是過時資料（例如半年前的購買階段），生成的話術會失真甚至造成客戶困擾。

↓ 解決方案

每日排程自動重算「近兩年」滾動窗口，每次執行以 DROP + CREATE + INSERT 全量覆寫，確保檢索結果不含過期或重複資料

Output Structure

三層 RAG 知識庫結構

層級單位用途
公司彙整公司近兩年活動數、最新購買階段、各角色痛點/需求分欄——下游查「這家公司整體現況」
