Background

這個平台在解決什麼問題？

團隊有多支爬蟲（純 API 下載型、需要瀏覽器渲染的 Chrome 型），過去只能在本機手動執行，沒有排程、沒有容器隔離、也沒有版本控制——改一行程式碼不知道是誰改的，換一台機器就要重新設定環境。需要一個能讓爬蟲「定期自動跑、壞了會通知、程式碼有歷史紀錄」的平台。

😣 過去的痛點

  • 爬蟲只能手動執行，沒有排程機制，容易忘記跑或跑到一半中斷
  • 輕量 API 爬蟲與需要瀏覽器渲染的爬蟲環境需求差異大，混在一起管理容易互相干擾
  • 程式碼只存在單一台機器上，沒有版本紀錄，換機器或多人協作都很麻煩
  • 沒有排程失敗通知機制，爬蟲掛掉往往要等到有人發現資料沒更新才知道

✅ 平台如何解決

  • Docker 容器化兩種爬蟲類型，各自獨立映像檔，互不干擾
  • Airflow DAG 排程觸發，內建重試機制與失敗 Email 通知
  • 自架 GitLab 做版本控制，Windows 本機開發、伺服器端 git pull 直接同步
  • 建立標準化部署與新增使用者流程，任何人都能照文件複製一套環境
How It Works

系統如何運作？

為什麼要拆成兩種容器化爬蟲？

純 API 下載型爬蟲只需要輕量的 Python 環境，但需要瀏覽器渲染的爬蟲得帶著完整的 Chrome 執行環境，映像檔動輒大上好幾倍。把兩者拆成獨立的 Docker 映像檔（scraper-light / scraper-browser），輕量任務不用背著 Chrome 的重量執行，資源使用更有效率，也讓兩種爬蟲可以獨立版本管理、獨立重建。

1

基礎環境建置

CentOS Stream 主機安裝 Docker Engine 與 Docker Compose，設定開機自動啟動，並以 SSH 金鑰綁定自架 GitLab 帳號。

建立標準化目錄結構：爬蟲程式碼、Airflow DAG、logs 各自獨立資料夾，並針對 Airflow container 內部使用者權限設定對應的目錄擁有權
2

Airflow 初始化

以 Docker Compose 啟動 Airflow webserver、scheduler 與 PostgreSQL 後端資料庫，初始化 metadata 資料庫並建立管理員帳號。

敏感設定（DB 密碼、Fernet 加密金鑰）統一放在 .env 檔案，並加入 .gitignore 排除版控，避免機密資訊進入 Git 歷史
3

容器化爬蟲部署

兩種爬蟲各自撰寫 Dockerfile 與 requirements.txt，透過 Docker Compose 統一編排，各自在獨立容器中執行。

4

DAG 排程設定

以 DockerOperator 撰寫 Airflow DAG，每個排程任務啟動對應的爬蟲容器、執行完自動清除，並設定失敗重試與 Email 通知。

5

Git 化開發流程

從最初用 scp 手動上傳檔案，逐步改為 Windows 本機開發 → push 到自架 GitLab → 伺服器端 pull 並重建容器的標準工作流程，程式碼異動全程可追蹤。

Security Maintenance

上線後的資安維護：當日應對高風險 CVE

⚠️ WSL2 核心高風險漏洞（CVSS 7.8）應變紀錄

開發環境的 WSL2 Linux 核心被揭露一個可讓本機使用者取得 root 權限的高風險漏洞。收到情資後，當天完成影響範圍盤點（確認 Windows 主系統不受影響，WSL2 子系統落在受影響版本區間）、執行核心更新、並驗證更新後版本已脫離受影響區間，同時建立每月固定檢查更新的維護習慣。

項目內容
影響範圍盤點比對主系統與 WSL2 子系統的核心版本，確認實際受影響的環境
修補執行更新 WSL2 核心並重啟子系統套用新版本
修補驗證更新後重新檢查核心版本號，確認已脫離受影響區間
後續預防建立每月固定執行更新檢查的維護排程，並確認系統自動更新設定已開啟
Engineering Challenges

解決了哪些技術難題？

Challenge 1

資料庫連線字串裡的特殊字元陷阱

密碼若含有 @、+、* 等特殊符號，環境變數展開後容易被連線字串誤判為分隔符，導致資料庫連線失敗且錯誤訊息不直觀。

↓ 解決方案

制定密碼命名規則排除特殊符號，並在 docker-compose 中直接寫死完整連線字串，避免環境變數展開時的二次解析問題

Challenge 2

容器內部使用者權限與宿主機不一致

Airflow container 內部固定使用 UID 50000 執行，若掛載的 logs 目錄權限沒對應設定，容器會因為寫入權限不足而啟動失敗。

↓ 解決方案

部署時將 logs 目錄擁有者設為對應 UID，並開放群組寫入權限，確保容器與宿主機的權限模型互相相容

Challenge 3

機密資訊不能進版控，但團隊要能重建環境

資料庫密碼、Airflow 加密金鑰等機密資訊若寫入 Git，會永久留在版本歷史裡難以清除；但完全不留紀錄又會讓換機器或新成員難以重建環境。

↓ 解決方案

機密設定統一集中在 .env 並加入 .gitignore，Git 裡只留 .env 的範例格式；換機器時的還原流程明確記錄「需手動重建 .env」這一步

Challenge 4

從手動 scp 到全版控的開發流程遷移

最初以 scp 手動上傳檔案到伺服器，容易漏傳、覆蓋別人的改動，且完全沒有歷史紀錄可追溯。

↓ 解決方案

導入自架 GitLab，建立「本機 push → 伺服器 pull → 重建容器」的標準流程，取代手動檔案傳輸，讓每次異動都有 commit 紀錄可查
